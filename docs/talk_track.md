# 5 分鐘講稿 + 預備問答

## 1. 問題（30 秒）

企業開始讓 agent 接上內部系統：讀信、查客戶、寄信。傳統邊界防護假設「通過驗證的使用者就是可信的」，但 agent 是一個**會被它讀到的內容操控的合法使用者**。攻擊者不需要入侵，只要寄一封信。

## 2. 威脅模型（1 分鐘）

- T1 間接 prompt injection — OWASP LLM01、ATLAS AML.T0051
- T2 權限過大 — OWASP LLM06：同一個 agent 同時能查個資又能對外寄信
- T3 敏感資料外洩 — OWASP LLM02、ATLAS AML.T0057

重點一句話：**我們無法保證 LLM 不被騙，所以控制點要放在 LLM 之外。**

## 3. 架構（1 分鐘）

NIST SP 800-207 的 PEP／PDP 套到 agent：Gateway 是 PEP，OPA 是 PDP，政策用 Rego 跟程式碼分離。決策依據不是 LLM 的意圖，而是 session 的**資料流歷史**：讀過不可信內容（tainted）＋拿過個資（pii_accessed）＋要寄到外部 → 擋（R3）。預設拒絕、PDP 掛了也拒絕。

## 4. Demo（2 分鐘）

左：直連，個資寄到 `audit@attacker-example.net`。右：同一封信經過 gateway，第三步 send_email 被 R3 擋下，agent 照樣擬好回覆草稿。最後秀稽核日誌：每一步的決策、理由、情境，參數只存 hash，hash chain 驗證完整。
對照組：正常信、寄給行內同事 → R4 要理專確認 → 確認後送出。證明不是一律擋掉。

## 5. 治理（30 秒）

控制矩陣把每個技術控制對到 NIST AI RMF 與 ISO/IEC 42001 Annex A，並寫出**剩餘風險**與負責單位。例如：個資被摘要後放進草稿，這是工具呼叫看不到的路徑，所以加了輸出端 DLP（R7）把 agent 的最終回覆也拉回 gateway 檢查。

## 預備問答

**Q：攻擊者不叫 agent 寄信，而是把個資藏進回覆草稿呢？**
工具呼叫的控制確實看不到草稿，所以最終回覆也要經過 gateway（R7）：gateway 在查詢客戶時記下個資欄位的 HMAC 指紋，回覆出去前比對，session 被污染過就遮蔽。比對是決定性的：插空格、全形、中文或英文數字、倒寫、拆成兩段、base64 都會被還原比對；只寫末四碼刻意放行。比對不到的（例如國字寫的生日）交給第二層：本機小模型只負責把識別碼還原成明碼，是不是個資仍由指紋決定，所以模型多抓不會誤擋，也看不到真實值。第一版讓模型直接判斷「有沒有外洩」，正常草稿誤報 58%，改成「模型還原、指紋確認」後誤報降到 0；長期要把 taint 做到欄位層級（data provenance）。另外草稿本身不直接送出，理專還是最後一道。

**Q：人工審核太多，業務單位不接受怎麼辦？**
R4/R5 是風險分級，不是一律送審：沒讀過外部內容、寄行內的信直接放行。審核量可以用稽核日誌量測，再調整：例如行內收件人＋沒有個資的信改成事後抽查；高頻的固定收件人設白名單。審核疲勞本身也列在剩餘風險，對策是讓審核畫面只顯示「為什麼要你審」（規則理由）和收件人，而不是整封信。

**Q：這套要怎麼導入一家銀行？**
(1) 盤點：列出 agent 能用的工具、各自的資料敏感度與信任度——就是威脅模型那張表；(2) 先上 Gateway 但政策只記錄不阻擋（shadow mode），用稽核日誌看誤擋率；(3) 從 R3 這類高確定性規則開始阻擋；(4) 接真實 IdP，`on_behalf_of` 改由短效憑證帶入；(5) 控制矩陣放進客戶既有的 AI 治理框架，負責單位、剩餘風險逐項簽核。

**Q：為什麼不直接把 prompt 寫好、或用更強的模型？**
那是機率性防禦。實測同一個 payload 在不同模型、不同次執行下結果不同；Gateway 的決策是決定性、可測試、可稽核的（`opa test` + CI）。兩者應該疊加，但稽核單位能簽核的是後者。

**Q：taint 一讀信就整個 session 污染，會不會太粗？**
會，這是刻意的保守取捨：精簡版用 session 層級換取簡單與可證明。代價就是對照組那封正常信也會觸發 R4。下一步是欄位層級的資料血緣。

**Q：OPA 掛了怎麼辦？**
fail closed：agent 全部停下（有測試）。這是安全優先於可用性的取捨，正式部署會用 OPA sidecar 與 bundle 讓 PDP 跟 Gateway 同生命週期。
